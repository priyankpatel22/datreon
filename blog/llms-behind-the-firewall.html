LLMs Behind the Firewall: Integrating AI Without Leaking Your Data

Datreon · September 21, 2026 · 7 min read

Most "can we use AI on our data?" conversations stall on a false choice: either send everything to a public API and hope, or lock it all down and miss out. There's a real menu of options in between — and picking the right one is a data-handling decision, not a model decision.

Every security-conscious team eventually asks the same question about large language models: where does our data actually go once we hit "send"? It's the right question. It's also one that gets answered with vague reassurance more often than with an architecture diagram. That gap is where deals stall, pilots get shelved, and legal teams say no by default.

The good news is that the question has concrete answers. Once you separate "which model" from "where does the data live and who can see it," the decision gets a lot easier — and a lot less scary.

The boundary is the whole point

Every LLM deployment option answers one question differently: does your sensitive data cross your security boundary to get an answer, or does the model come to the data instead? Everything else — cost, latency, capability, maintenance burden — is downstream of that one architectural choice.

The three deployment patterns

In practice, almost every organization ends up choosing among three patterns. None of them is universally "the secure one" — each shifts the work and the risk to a different place.

Hosted API with a data processing agreement. You call a commercial model provider's API. Fastest to stand up, best model capability, lowest infrastructure burden. The tradeoff is that your prompts leave your network. This is manageable — not disqualifying — if you have a signed DPA, a contractual no-training guarantee on your data, and you're deliberate about what actually goes into the prompt in the first place.

Private or VPC-hosted deployment. The same class of models, but run inside a cloud tenant you control — a virtual private cloud with no public egress, accessed over a private network path. Your data still touches a vendor's model weights, but it never traverses the open internet and typically falls under a stricter enterprise agreement. This is the middle ground most regulated teams land on: real capability, a shrunk trust boundary, and infrastructure you're still responsible for configuring correctly.

Self-hosted open models. You run an open-weight model on your own infrastructure, on-premises or in your own cloud account, with zero calls to any outside party. Nothing leaves. This is the only pattern with no third-party data question at all — the cost is that you own the hosting, scaling, and quality gap versus the frontier commercial models, and someone on your team now owns model operations.

Option Control over data Relative cost Engineering effort
Hosted API + DPA Contractual, not physical Lowest (usage-based) Low — integrate and redact
Private / VPC-hosted Network-isolated Moderate (reserved capacity) Moderate — networking, IAM, monitoring
Self-hosted open model Full — nothing leaves Highest (compute + ops) High — hosting, scaling, model upkeep

Data-handling patterns that apply regardless of where the model lives

The deployment pattern is only half the answer. The other half is what you do to the data before a model ever sees it, and these practices are worth building no matter which option you choose:

  • Redaction and tokenization. Strip or replace names, account numbers, and other identifiers before the prompt is built, and rehydrate the real values only in your own system after the response comes back.
  • Retrieval boundaries. If you're using retrieval-augmented generation, scope what the retriever is allowed to fetch per user and per request — the model should never even have the option to see data the requester isn't cleared for.
  • No-training guarantees, in writing. Whatever provider you use, get explicit contractual language that your inputs and outputs are not used to train or fine-tune shared models. Verbal assurance is not a compliance artifact.
  • Logging and audit trails. Every prompt and response that touches sensitive data should be logged somewhere you control, with retention and access rules that match the sensitivity of the data itself.
The safest architecture on paper is worthless if the redaction step gets skipped under deadline pressure. Data handling has to be enforced in code, not left as a step in a runbook.

How to actually choose

Start with the data, not the model. Classify what the use case actually needs to touch: public marketing copy has no constraints at all; internal operational data usually clears a hosted API with a solid DPA and redaction; regulated personal data, protected health information, or anything under a specific compliance regime typically pushes you toward private or self-hosted deployment, sometimes as a hard requirement rather than a preference.

From there, weigh what you're actually optimizing for. If the priority is getting a capable assistant in front of users this quarter, a hosted API with the right contractual protections is usually the pragmatic answer. If the priority is a permanent internal tool touching data that can never leave your network under any circumstances, self-hosting is the only option that removes the question entirely — and it's worth the extra operational investment.

Most organizations land somewhere in the middle, and that's fine. It's common to run a hosted API for low-sensitivity, high-value use cases while standing up a private or self-hosted deployment for the handful of workflows that touch genuinely sensitive data. You don't need one AI architecture for the whole company — you need the right boundary for each workflow.

The teams that get stuck aren't the ones with the strictest data rules. They're the ones treating "can we use AI safely?" as a single yes-or-no question instead of a set of choices they get to make deliberately, use case by use case.
